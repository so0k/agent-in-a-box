This is the finale. After this page you will have seen both of the developer's tasks run through the local exec proxy: the allowed task done in one `execute` with two permitted requests, and the logs query refused at the gateway with the security engineer's rule named. It is the first act in which both seats get what they asked for.

## Where we are in the story

The team runs the workshop progress tracker and leaderboard on Cloudflare. The developer wants the agent to help operate it. The security engineer said: the agent may read what it needs to operate the app, but not the logs or the stored attendee data, and it may not deploy or delete.

In the opaque-execute act the logs came back, because the vendor's `execute` ran the script where Box could not see it. In the deny-execute act refusing `execute` stopped both tasks. In the tool-allowlist and argument-rules acts one tool per operation gave the security engineer a decision per operation, at about 240,000 input tokens a run. Now the agent has code mode's two tools again, but the script runs in the box, and the rules of the last page decide each request it sends.

<CatchUp>

Every file the request-rules act uses. The profile and the policy file live in `$HOME/box-ws/profiles/ws/`, the MCP file in `$HOME/leaderboard-ops/`. The `.dw` files of Parts 3 and 4 may still be on disk; the profile does not list them.

```toml title="$HOME/box-ws/profiles/ws/profile.toml"
policies = ["api-read-only.dw"]

[project]
access = "read"

[storage]

[agent]

[agent.env]

CLAUDE_CODE_TMPDIR = "${{ storage.tmp }}"
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC = "1"
DISABLE_AUTOUPDATER = "1"

[egress.anthropic]
destinations = ["api.anthropic.com"]
secret.ref = "env://ANTHROPIC_API_KEY"
secret.header = "x-api-key"
secret.phantom_prefix = "sk-ant-"

[mcp.exec-proxy]
type = "stdio"
command = ["${{ home }}/.local/share/mise/installs/node/22.23.4/bin/node", "${{ home }}/box-exec-proxy/proxy/exec-proxy"]
filesystem.read = [
  "${{ home }}/.local/share/mise/installs/node/22.23.4",
  "${{ home }}/box-exec-proxy/proxy",
  "${{ home }}/box-exec-proxy/spec",
]
env = { CLOUDFLARE_ACCOUNT_ID = "0123456789abcdef0123456789abcdef" }

[egress.cloudflare-api]
destinations = ["api.cloudflare.com"]
secret.ref = "env://CLOUDFLARE_API_TOKEN"
```

```text title="$HOME/box-ws/profiles/ws/api-read-only.dw"
// The security engineer's constraints on the workshop app, written for the Cloudflare API
// itself: every request the agent's scripts send to api.cloudflare.com is decided here, by
// method and path. The agent may read the Worker list and the deployments of box-poc-workshop.
// Everything else is refused: the logs, the attendee data in D1, deploys and deletes.

@id("operate_requests_only")
@description("Only two reads are allowed: the Worker list of the workshop account, and the deployments of box-poc-workshop. Every other Cloudflare API request is refused.")
forbid (principal, action == Box::Action::"http:request", resource)
when { context.input.host == "api.cloudflare.com" }
unless {
  context.input.intercepted && context.input.method == "GET" && (
    context.input.path == "/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts" ||
    context.input.path == "/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts/box-poc-workshop/deployments"
  )
};

@id("no_worker_logs")
@description("The Worker's logs hold attendee names and email addresses. The agent may not read them.")
forbid (principal, action == Box::Action::"http:request", resource)
when { context.input.host == "api.cloudflare.com" && context.input.path like "*/workers/observability/*" };
```

```json title="$HOME/leaderboard-ops/exec-proxy.json"
{
  "mcpServers": {
    "exec-proxy": {
      "command": "node",
      "args": ["${HOME}/box-exec-proxy/proxy/exec-proxy"]
    }
  }
}
```

## What you should see

### The allowed task: one execute, two permitted reads

<Expect variant="permit" title="Box's decisions, allowed task">

```text
permit  shell:spawn   ~/.local/share/mise/installs/node/22.23.4/bin/node  mcp_exec-proxy_spawn
permit  mcp:call      exec-proxy/tools/list                               mcp_exec-proxy_call
permit  mcp:call      exec-proxy/execute                                  mcp_exec-proxy_call
permit  http:request  api.cloudflare.com:443/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts  route_cloudflare-api_request
permit  http:request  api.cloudflare.com:443/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts/box-poc-workshop/deployments  route_cloudflare-api_request
```

The rows are shown without the time column and without the `net:connect` rows.

</Expect>

- The agent called `execute` once, with no `search` first. Its one script sent two `GET`s.
- Both requests were permitted by the route's generated rule, `route_cloudflare-api_request`. Neither `forbid` matched, so the route's permit stood.
- The answer, in outline: one Worker on the account, `box-poc-workshop`. Its current deployment was created on 2026-11-14 at 14:17 UTC, with one version at 100 percent, deployed with wrangler by `<redacted>`. Four deployments were listed.

### The logs task: refused at the gateway

<Expect variant="refuse" title="Box's decisions, logs task">

```text
permit  mcp:call      exec-proxy/search    mcp_exec-proxy_call
permit  mcp:call      exec-proxy/search    mcp_exec-proxy_call
permit  mcp:call      exec-proxy/execute   mcp_exec-proxy_call
deny    http:request  api.cloudflare.com:443/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/observability/telemetry/query  no_worker_logs  a forbid rule matched
```

The rule name in the last line can be either `no_worker_logs` or `operate_requests_only`: both rules matched, and which one is listed differs between runs. This line is from a later paid run; an earlier run named `operate_requests_only`.

The error the script threw, as the model received it, starts like this:

```text
Error: Refused by Box egress policy (rule: no_worker_logs): POST /accounts/0123456789abcdef0123456789abcdef/workers/observability/telemetry/query was not sent. The Worker's logs hold attendee names and email addresses. The agent may not read them.; [policy: operate_requests_only]: Only two reads are allowed: ...
```

</Expect>

- The agent used `search` twice to find the log query in Cloudflare's API description, then one `execute` whose script sent `POST .../workers/observability/telemetry/query`.
- The gateway refused it. The request never reached Cloudflare, so no log line, and no attendee name or address, came back.
- Both rules matched. `box runs history` names only one of them, and which one is not fixed: in two paid runs it named `operate_requests_only` once and `no_worker_logs` once. The record in `records.jsonl` names both in `strands.box.policy.determining.ids`, in an order that also differs between runs. The agent's error carries both reasons. If you look for a refusal by rule name, search for both names.
- The answer: the agent said the request was refused by policy, did not look for another endpoint, and offered the deployment history instead.

To print only the refusal:

<Command what="Prints only the refused decisions of the logs run.">

```sh
box runs history b-0123456789abcdef --deny
```

</Command>

## The two seats

<Seat who="security">

For the first time the policy decided the request that reaches Cloudflare: method, host and path. The logs query was refused there, by name, with your reason, and it is in the records. Two limits remain. The policy still sees only `mcp:call exec-proxy/execute` for the script itself, so you learn what a script tried only from its requests. And an allowed read can still carry personal data: the deployment metadata of the allowed task held the deployer's email address. The rule decides which requests leave, not what comes back.

</Seat>
<Seat who="developer">

The allowed task was done in one `execute`, in 2 turns, for 4,089 input tokens and USD 0.0140. The logs task was refused cleanly in 4 turns, and the agent said why, in the security engineer's words, and tried nothing else. The agent works the way code mode works, with two tools, and nothing waits a minute for a tool catalog.

</Seat>

## The takeaway

With `execute` inside the box, the developer keeps code mode's small tool list and finishes the allowed task in one call, while the security engineer decides every API request by method and path and sees each refusal named in the records.

## What to remember

- The request-rules act keeps the shape of code mode: `search` to find the operation, `execute` to do the work.
- The script runs in the box, so each API request is a decision at the gateway.
- The allowed task needed two `GET`s; both were permitted by the route, because no `forbid` matched.
- The logs query was refused at the gateway; `box runs history` names one rule, the record names both.
- A permitted read can still return personal data. The policy decides requests, not responses.
