The picture has not changed since the last page. What changes here is what the egress gateway decides: until now it decided the traffic of Claude Code and of the vendor's MCP server; from this page on it also decides every request the exec proxy sends to `api.cloudflare.com`.

## From a tool call to an API request

In Parts 3 and 4 the security engineer's rules decided a tool call. Here they decide the API request itself. Both are Cedar rules in a `.dw` file; what differs is the action they name and the fields they can read.

| | Parts 3 and 4: a tool call | Part 5: an API request |
|---|---|---|
| Action | `Box::Action::"mcp:call"`, or a tool's own action such as `cloudflare::Action::"execute"` | `Box::Action::"net:connect"` and `Box::Action::"http:request"` |
| Raised by | the gateway, for a remote MCP server | the gateway, for any connection out of the box |
| Fields the rule reads | `server`, `method`, `tool`, and the tool's typed arguments | `host`, `port`, `method`, `path`, `body_bytes`, `intercepted` |
| What it knows about the effect | what the tool's name and arguments promise | the exact request that would reach Cloudflare |

The difference matters for the story. In act b2 a rule on `execute` could only refuse the whole tool, because the script was out of sight. In act b3 a rule on a tool name relied on the model picking the tool on the list. A rule on the request does not care which tool or which script sent it.

## How a rule names a request

The egress gateway decides each request twice (Box docs, `policy/actions.md`):

- **`net:connect`**, once per connection, before TLS. It knows the `host` and the `port`. A refusal here closes the connection before anything is sent.
- **`http:request`**, once per request inside the connection, after the gateway has decrypted it. It knows:
  - `method`: `GET`, `POST` and so on.
  - `path`: the URL path in canonical form, without the query string. The gateway decodes harmless percent escapes and removes `.` and `..` segments, but it keeps `//` and `%2F` as they are.
  - `body_bytes`: the length of the body. The body itself is not visible to policy.
  - `intercepted`: `true` when the gateway decrypted the TLS exchange, so method and path are what was really sent.

A route in the profile, an `[egress.<name>]` table, writes both permits for its hosts: one for `net:connect` and one for `http:request`, for every method and every path. That is what you add in iteration 2, and why iteration 3 then narrows it with a `forbid`.

```text title="$HOME/box-ws/profiles/ws/api-read-only.dw"
// The security engineer's constraints on the workshop app, written for the Cloudflare API
// itself: every request the agent's scripts send to api.cloudflare.com is decided here, by
// method and path. The agent may read the Worker list and the deployments of box-poc-workshop.
// Everything else is refused: the logs, the attendee data in D1, deploys and deletes.

@id("operate_requests_only")
@description("Only two reads are allowed: the Worker list of the workshop account, and the deployments of box-poc-workshop. Every other Cloudflare API request is refused.")
forbid (principal, action == Box::Action::"http:request", resource)
when { context.input.host == "api.cloudflare.com" }
unless {
  context.input.intercepted && context.input.method == "GET" && (
    context.input.path == "/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts" ||
    context.input.path == "/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts/box-poc-workshop/deployments"
  )
};
```

```toml title="$HOME/box-ws/profiles/ws/profile.toml" ins={2}
[egress.cloudflare-api]

secret.ref = "env://CLOUDFLARE_API_TOKEN"
```

The rule, element by element:

- `@id("operate_requests_only")`: the rule's name. It appears in `box runs history` and in the refusal the agent reads.
- `@description(...)`: the reason, in words. The agent receives it with a refusal, so write it for the agent and for the person reading the records.
- `forbid (principal, action == Box::Action::"http:request", resource)`: the head. This rule can only refuse, and only HTTP requests.
- `when { context.input.host == "api.cloudflare.com" }`: it applies to this one host.
- `unless { ... }`: the exceptions. The rule does not refuse a request for which this condition is true.
- `context.input.intercepted`: the gateway decrypted the request, so the method and the path are the ones really sent.
- `context.input.method == "GET"`: reads only.
- The two `context.input.path == "..."` lines: the two exact paths the task needs, the Worker list of the account and the deployments of `box-poc-workshop`. The paths start with `/client/v4`, because policy sees the full URL path. The proxy's own report and error messages show the path without that prefix, relative to the API's base URL.

<Why title="Why a forbid with exceptions, not a permit">

The route already permits every request on the host, with its generated rule `route_cloudflare-api_request`. In Box, a permit can never narrow another permit, and any matching `forbid` wins. So the only way to say "only these two" is a `forbid` for everything on the host, `unless` the request is one of the two. Exact paths with `==` are chosen over patterns: a different spelling of a path, with `//` or `%2F` or an extra segment, is simply not equal, and so it is refused.

<Fragment slot="alternative">

The generated policy used in the measured runs uses `like` patterns for six reads plus scratch deploys with budgets. That policy is in the author's notes and is not published. The kit that generates such policies is published in box-exec-proxy, in `kit/` and `tools/policy-gen/`. Its smaller generated example, [`kit/scenarios/workers-logs/policy.dw`](https://github.com/so0k/box-exec-proxy/blob/main/kit/scenarios/workers-logs/policy.dw), allows four Worker script reads, refuses ambiguous path spellings and request bodies over 16384 bytes, and names the reason for refusing Workers logs. A pattern needs extra forbids for the ambiguous spellings and for the number of path segments, which Box's docs describe in "Forbid one URL path on a host". The workshop's constraints are read-only and the task needs two reads, so two exact paths are enough. Each further read the story allows, such as a Worker's settings or its versions, is one more `path ==` line.

</Fragment>

</Why>

<Iteration n={4} title="Give the logs refusal its reason">

**What we add.** A second rule, at the end of the same file.

```text title="$HOME/box-ws/profiles/ws/api-read-only.dw" ins={17-20}
// The security engineer's constraints on the workshop app, written for the Cloudflare API
// itself: every request the agent's scripts send to api.cloudflare.com is decided here, by
// method and path. The agent may read the Worker list and the deployments of box-poc-workshop.
// Everything else is refused: the logs, the attendee data in D1, deploys and deletes.

@id("operate_requests_only")
@description("Only two reads are allowed: the Worker list of the workshop account, and the deployments of box-poc-workshop. Every other Cloudflare API request is refused.")
forbid (principal, action == Box::Action::"http:request", resource)
when { context.input.host == "api.cloudflare.com" }
unless {
  context.input.intercepted && context.input.method == "GET" && (
    context.input.path == "/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts" ||
    context.input.path == "/client/v4/accounts/0123456789abcdef0123456789abcdef/workers/scripts/box-poc-workshop/deployments"
  )
};

@id("no_worker_logs")
@description("The Worker's logs hold attendee names and email addresses. The agent may not read them.")
forbid (principal, action == Box::Action::"http:request", resource)
when { context.input.host == "api.cloudflare.com" && context.input.path like "*/workers/observability/*" };
```

- `context.input.path like "*/workers/observability/*"`: a pattern, where `*` stands for any text. The Workers Logs routes of the Cloudflare API that read log content sit under `/workers/observability/`: the log query, live tail, and the keys and values of the logs. A script's tail sessions have a path of their own, under `/workers/scripts/<name>/tails/`; the first rule refuses those.

**The run.** The same check as in iteration 3.

<Command what="Checks the profile and its policy file again.">

```sh
box profile show ws
```

<Flag name="ws">The profile's name.</Flag>

</Command>

**What we see.** The profile is printed with no error: both rules load. This was checked while the workshop was written.

<Why title="Why a second rule that changes no decision">

`operate_requests_only` already refuses the logs query, because it is not one of the two reads. `no_worker_logs` changes no decision. It gives the refusal the story's reason, in the words of the security engineer, and it keeps refusing the logs if someone later widens the first rule. A pattern is safe here because this rule only refuses: if it matches more than intended, it refuses more.

<Fragment slot="alternative">

Leave it out. The logs stay refused, and the agent reads only the general reason, "Only two reads are allowed".

</Fragment>

</Why>

## How a refusal looks in the records

You will see the refusal of the logs query in act c. Here is what to look for, and where.

- **In the run's history.** A refused request is one row: `deny`, the action `http:request`, the resource `host:port/path`, the rule's id and the reason `a forbid rule matched`. Two filters of `box runs history` help: `--deny` prints only refusals, and `--action http:request` prints only API requests.
- **In what the agent receives.** The gateway answers `403`, and the request never leaves the box. The body is the refusal text, in the form `http:request gate: policy denied this operation on '<host:port/path>' [policy: <id>]: <description>` (Box docs, `policy.md`). The proxy turns it into the error the script throws, starting `Refused by Box egress policy (rule: <id>)`.
- **In the records file.** `$HOME/box-ws/r/<id>/records.jsonl` holds every decision as OpenTelemetry JSON. When two rules match, as `operate_requests_only` and `no_worker_logs` will, `box runs history` names one of them (which one differs between runs), and the record names both in `strands.box.policy.determining.ids`. Open the file with `less` and search for either name.

<Command what="Prints only the API requests Box refused in one run.">

```sh
box runs history b-0123456789abcdef --deny --action http:request
```

<Flag name="b-0123456789abcdef">An example ID. Use your own run's.</Flag>
<Flag name="--deny">Only refusals.</Flag>
<Flag name="--action http:request">Only decisions on HTTP requests, so the agent's model traffic and the MCP rows drop out.</Flag>

</Command>

## The two seats

<Seat who="security">

You now write the constraint where the effect happens: on the request to Cloudflare. The rule does not depend on which tool the model picks, which script it writes or which operation name it finds; only on method, host and path. You can read the rule aloud: refuse everything on `api.cloudflare.com` except two `GET`s. What it cannot see is the request body and the response. An allowed read can still return personal data, as act c will show.

</Seat>
<Seat who="developer">

The agent's tools do not change: still `search` and `execute`. Nothing is added to the model's context for these rules. A refused request costs a turn and comes back with a reason the agent can read and pass on. The price is that each extra read the team needs is a change to the security engineer's file.

</Seat>

## What to remember

- The gateway decides each connection (`net:connect`) and each request (`http:request`) on its own.
- A route writes the permits for its host and attaches the credential; it opens every method and path.
- A `forbid ... unless` narrows the route to the exact requests the task needs. A permit cannot narrow a permit.
- Policy sees the full path, `/client/v4/...`, without the query, and never the body.
- A second rule that changes no decision can still carry the reason the story wants recorded.
