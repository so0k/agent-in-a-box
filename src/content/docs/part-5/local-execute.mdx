## Where Part 4 left the two seats

Each act so far traded one thing for another.

- In the opaque-execute act the vendor's `execute` ran the agent's script on Cloudflare's side. Box saw one `mcp:call` for `execute` and no request to `api.cloudflare.com` at all. The logs came back.
- In the deny-execute act the security engineer refused `execute` by name. Both tasks were refused, the harmless one too.
- In the tool-allowlist and argument-rules acts the vendor's server offered one tool per API operation, 3,053 of them. The policy could decide each operation and even its arguments. The developer paid for it: 246,000 to 329,000 input tokens and 77.5 to 81.8 seconds per run, measured on 2026-11-24 on the fork build (see [Measurements](/results/measurements/)).

The question for Part 5: can the developer keep the small tool list of code mode while the security engineer still decides every API request?

## The idea: keep code mode, move execute

Code mode gives the agent two tools. `search` finds an operation in the API's description. `execute` runs a short script the agent writes, and that script makes the API requests. One call can do several requests, and the tool list stays small. Some servers call the same idea `execute_script`; the tool in this workshop is named `execute`.

What matters for the security engineer is where the script runs.

| | Vendor's `execute` (opaque-execute, deny-execute) | Local `execute` (request-rules) |
|---|---|---|
| Where the script runs | on Cloudflare's side, behind `mcp.cloudflare.com` | inside the box, in the exec proxy's own sandbox |
| What leaves the box | one MCP request that holds the whole script | one HTTPS request per API call the script makes |
| What Box can decide | the tool call: server, method, tool name | the tool call, and then every API request: method, host, path |
| Which token is used | the MCP token, held on the vendor's side | the API token, added by Box's gateway |

So the local proxy does not make the agent see less or do less. It moves the API requests to a place where Box already decides every request: the egress gateway.

## The design of the local exec proxy

The proxy is a proof of concept in the [box-exec-proxy](https://github.com/so0k/box-exec-proxy) repository, under `proxy/`. It is a small Node 22 program with no dependencies, an MCP server that speaks JSON-RPC over standard input and output (a "stdio" server). Its own README says it plainly: it is "a convenience tool, not a security component". Box is the sandbox and the place where requests are decided. The proxy holds no policy and no real secret.

### Two tools, copied from the vendor

The two tools have the same names, argument shapes and annotations as the tools of Cloudflare's own code mode (source: `proxy/lib/tools.js`).

- `search` takes `code`, a JavaScript async arrow function, and an optional `truncate`. It runs the function with `spec` in scope: Cloudflare's OpenAPI description, read from `spec/spec.json` beside the proxy. It makes no network call.
- `execute` takes `code`, an optional `account_id` and an optional `truncate`. It runs the function with three things in scope: `cloudflare.request({ method, path, query, body, contentType })`, the constant `accountId`, and `fetch`. It returns what the function returns, plus a report of every outbound call: its method, its path and what happened to it (sent with a status, refused with a rule, failed, not sent).

`accountId` is the `account_id` argument if the agent gives one, otherwise the server's `CLOUDFLARE_ACCOUNT_ID` variable. The profile sets that variable in the last iteration below.

### How execute runs a script

From `proxy/lib/execute.js` and `proxy/lib/sandbox-worker.js`:

1. The proxy starts a Node worker thread with an empty environment, so the token never reaches the script's thread. The worker has a 512 MB memory cap and a 60 second time limit, and at most 8 scripts run at once.
2. The worker runs the agent's code in a fresh `node:vm` context that exposes only `cloudflare.request`, `accountId`, `fetch` and basic globals. Node's own documentation says `node:vm` is not a security mechanism, and the proxy does not rely on it. Box is the boundary.
3. Each `cloudflare.request` or `fetch` becomes a message to the proxy's main thread. The main thread sends a real HTTPS request to `https://api.cloudflare.com/client/v4` plus the path, with an `Authorization: Bearer` header built from its `CLOUDFLARE_API_TOKEN` variable.
4. Limits, for hygiene and not for security: 50 calls per script, 30 seconds per call, 10 MB per response, 24,000 characters of result unless `truncate` is turned off.

### Why every request must pass Box's gateway

The proxy cannot send a request around Box, for three reasons that come from Box, not from the proxy.

- Box starts the proxy in its own sandbox. The proxy reaches only the files the profile grants it (iteration 4 below).
- The proxy's network is contained. The `network.contain_egress` setting of an `[mcp.<name>]` table defaults to `true`: the box sets `HTTPS_PROXY` for the server, so every connection goes to the egress gateway, where policy decides each `net:connect` and each `http:request` (Box docs, `mcp.md`, "Network"). Node's `fetch` follows that variable. The profile on this page leaves the setting at its default.
- The proxy never holds the real token. Its `CLOUDFLARE_API_TOKEN` holds a stand-in, and the gateway swaps the stand-in for the real token only on a request that policy permits, for the hosts of the route (next page).

When the gateway refuses a request, it answers `403` and the request never reaches Cloudflare. The proxy reads that answer and throws an error inside the script that starts with `Refused by Box egress policy (rule: <id>)`. The agent sees it in the tool result. The proxy reports the refusal; it never decides one.

## How Box starts it: two declarations that must agree

In Part 2 the Cloudflare server was remote. Claude Code learned its URL from the `--mcp-config` file, and the profile's `[mcp.cloudflare]` table named its host in `destinations`. Box matched the requests to that host and decided them as `mcp:call`.

A local server is a program, not a URL, so the two declarations name a program.

| | Claude Code's file, `exec-proxy.json` | The profile's `[mcp.exec-proxy]` table |
|---|---|---|
| Read by | Claude Code | Box |
| Says | run `node` with one argument, the proxy's path | the server's type (`stdio`), the exact program and arguments, its files, its environment |
| Path spelling | `${HOME}/...`, filled in by Claude Code | `${{ home }}/...`, filled in by Box |

Box puts a stand-in program, an alias, on the agent's `PATH`, named after the file name of the profile's program: here `node`. When Claude Code runs `node` with the same arguments in the same order, Box asks policy (`shell:spawn`, with the generated rule `mcp_exec-proxy_spawn`), starts the declared program in its own sandbox, and passes the MCP messages through its MCP broker. The broker decides each `mcp:call` (generated rule `mcp_exec-proxy_call`) and reads the server's `tools/list` to type each tool.

If the two declarations differ, the alias runs the next ordinary program of that name on the agent's `PATH`, with no MCP checks at all (Box docs, `mcp.md`). In this workshop's box there is no other `node` on the agent's `PATH`, so the start simply fails. Measured in an earlier test with a scratch server: `strands-box: no ordinary executable for "node" on the agent's PATH`, exit status 127.

The second line is Box's start-up report warning that a Node server (this report line is also printed by Box 0.3.0, measured with the finished profile of the request-rules act) can run any program it can reach and load code from where it can write. In this profile it can write nowhere.

<Why>

An absolute path for Node selects exactly that program, whatever else is on a `PATH`. Box generates `mcp_exec-proxy_spawn`, which pins that exact program path, so the security engineer knows which program starts.

<Fragment slot="alternative">

A bare `node` as element 0 would be looked up on the `PATH` of the shell that runs `box run`: whichever `node` comes first there would start. A launcher file with a `#!` line, which the old demo used, is not needed: the command above was checked without one.

</Fragment>

</Why>

</Iteration>

<Iteration n={4} title="Give the server its files">

**What we add.** One list, `filesystem.read`, with three folders the server may read.

```toml title="$HOME/box-ws/profiles/ws/profile.toml" ins={22-26}
# Written by `box profile create`. Your values go here, and the packs hold the rest.
# `box profile show ws` prints what a run gets.
# For help from a coding agent, tell it: Run box help agent and follow it.
packs = ["@box/claude", "@box/anthropic"]
policies = ["policy.dw"]

# How much of your project the agent reaches: "none", "read", "write".
[project]
access = "read"

[options]
claude.host = "anthropic"
claude.import-mcp = "false"
claude.import-hooks = "false"

[agent.env]
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC = "1"

[mcp.exec-proxy]
type = "stdio"
command = ["${{ home }}/.local/share/mise/installs/node/22.23.4/bin/node", "${{ home }}/box-exec-proxy/proxy/exec-proxy"]
filesystem.read = [
  "${{ home }}/.local/share/mise/installs/node/22.23.4",
  "${{ home }}/box-exec-proxy/proxy",
  "${{ home }}/box-exec-proxy/spec",
]
```

- The Node folder: Node and its libraries. Box's docs say a server that runs on an interpreter such as Node needs `read` for the interpreter's install folder on macOS.
- `proxy`: the server's code.
- `spec`: Cloudflare's OpenAPI description, which `search` reads. The proxy looks for `spec/spec.json` next to its own `proxy/` folder by default, so no setting is needed to point at it.

**The run.** The free check of this part.

**What we see.** The server connects and offers its two tools.

<Aside type="note" title="Not run for this workshop">
This iteration's own check was measured earlier with the hand-written profile, on an earlier local build; not run again for this workshop. The end state, connected with two tools, is confirmed by the request-rules act's free check on Box 0.3.0, with a later profile that also holds the route and the rules.
</Aside>

<Expect variant="permit">

```text
"mcp_servers":[{"name":"exec-proxy","status":"connected"}]
permit  shell:spawn  ~/.local/share/mise/installs/node/22.23.4/bin/node  mcp_exec-proxy_spawn
permit  mcp:call     exec-proxy/tools/list                               mcp_exec-proxy_call
```

The `init` event lists the two tools `mcp__exec-proxy__execute` and `mcp__exec-proxy__search`. The whole free check took about 3 seconds (2.5 s in the request-rules act's free check on Box 0.3.0). With the per-endpoint catalog of Part 4 it took 67.5 s.

</Expect>

<Why>

Only read access, and only to the three folders the server needs. The server can write nowhere, so the "broad exec" warning of iteration 3 has nothing to load code from.

<Fragment slot="alternative">

`filesystem.write` would let the server keep files, for example a cache, and then it could also run what it wrote there. A `deny` list can close a path inside a granted folder. Neither is needed here.

</Fragment>

</Why>

</Iteration>

## The two seats

<Seat who="security">

Box now runs the code the model wrote, but inside the box, in a sandbox of its own that reads three folders and writes nowhere. For the tool call itself the policy still sees only `mcp:call exec-proxy/execute`: it does not read the script. What changes is everything after that: each API request the script makes leaves through the egress gateway and is a decision of its own. So far there is no route to `api.cloudflare.com`, so every such request would be refused. The proxy is not a security component; nothing on this page asks you to trust it.

</Seat>
<Seat who="developer">

The agent has the same two-tool shape as code mode: find the operation with `search`, do the work with `execute`. The proxy's tool list is 6,071 bytes, about 1,500 tokens by a bytes-divided-by-four estimate (not counted with the token counter). In the box 0.1.8 runs, the first model request of the request-rules act was 2,263 input tokens in all, system prompt included. The server is ready in seconds, not after a minute of staging.

</Seat>

## What to remember

- The local exec proxy keeps code mode's two tools, `search` and `execute`, and runs the script inside the box.
- Box starts a stdio server when the agent runs the alias with exactly the profile's command and arguments.
- The server's own sandbox needs file grants: Node, the proxy's code, the API description.
- The server's network is contained by default, so every request a script makes goes to the egress gateway.
- The proxy holds no policy and no real secret. Box decides; the proxy reports.
