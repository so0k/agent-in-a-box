In this act you write your first policy rule: a `forbid` that refuses the vendor's `execute` tool by name. You will see both tasks refused, the logs task and the allowed one, and you will see why: in code mode, `execute` is the only tool that does anything.

## Where we are in the story

In the opaque-execute act the agent ran in a box, and the logs of the workshop progress tracker still came back, with whatever attendee names and emails they held. Box saw one `mcp:call` for `execute` and permitted it, because the script ran on Cloudflare's side where Box cannot look. The security engineer's first constraint is that the agent must not read the logs or the stored attendee data. The bluntest way to enforce it with what Box can see is to refuse `execute` altogether.

## Write the rule

**The run.** Ask Box to resolve the profile before you write the file.

<Command what="Resolves the profile and checks its policy files, without starting a box.">

```sh
box profile show ws
```

<Flag name="ws">The profile's name. Box reads `$HOME/box-ws/profiles/ws/profile.toml` and every file it names.</Flag>

</Command>

**What we see.** Box refuses: the file does not exist yet. The `:2` is the line of `profile.toml` that names it. (Your terminal may wrap the line.)

<Expect variant="refuse">

```text
box: error: ~/box-ws/profiles/ws/profile.toml:2: `policies[0]` = "no-remote-execute.dw": cannot read ~/box-ws/profiles/ws/no-remote-execute.dw: No such file or directory (os error 2)
```

</Expect>

<Why>
`policies` is the profile's list of rule files. A name without a folder is read from the profile's own folder, so the file belongs next to `profile.toml`. The name says what the file is for: no script runs remotely, out of Box's sight.

<Fragment slot="alternative">
Several files are allowed (`policies = ["a.dw", "b.dw"]`); Box joins them in list order. One file per constraint keeps each one easy to remove, which you will do in the tool-allowlist act.
</Fragment>
</Why>

</Iteration>

<Iteration n={2} title="The rule, element by element">

**What we add.** Create `$HOME/box-ws/profiles/ws/no-remote-execute.dw` in your editor. It goes next to `profile.toml`:

<FileTree>

- box-ws/
  - profiles/
    - ws/
      - profile.toml you edit this
      - **no-remote-execute.dw** your first policy file
  - storage/ kept between runs
  - r/ one folder per run
- leaderboard-ops/ the workspace
  - cloudflare-code-mode.json

</FileTree>

Build the file in this order, reading each line as you type it.

1. **The comment** says which constraint of the story this file enforces. Box ignores lines that start with `//`; the next person to read the file does not.
2. **The id**, `@id("no_hidden_api_calls")`: the name that `box runs history`, the records and the agent's error text will show. It names the reason, not the tool.
3. **The description**: the sentence the agent receives when the rule refuses. It says why, and what to do instead.
4. **The effect**, `forbid`: the generated `mcp_cloudflare_call` already permits every tool, and a permit cannot narrow a permit ([Policy basics](/part-3/policy-basics/#a-permit-only-widens)).
5. **The scope**: `principal` and `resource` stay bare, as always in Box. The action is the per-tool action `cloudflare::Action::"execute"`. `cloudflare` is the name of your `[mcp.cloudflare]` table; `execute` is the tool's name in the server's tool list.
6. **No condition.** Every call to `execute` is refused, whatever its script says. The policy cannot read the script in a way that would let it tell a harmless one from a harmful one, so it does not try.

```text title="$HOME/box-ws/profiles/ws/no-remote-execute.dw"
// The security engineer's first constraint on the workshop app: the agent may not read
// the Worker's logs or the attendee data. Cloudflare's execute tool could do both, out of
// Box's sight, so it is refused by name.
@id("no_hidden_api_calls")
@description("Cloudflare's execute tool runs its script on Cloudflare's side, where Box cannot see which API calls it makes. Use a tool whose calls Box can decide.")
forbid (principal, action == cloudflare::Action::"execute", resource);
```

**The run.** First `box profile show ws` again: it passes now and lists `policies  no-remote-execute.dw`. Then the free check from [MCP through the broker](/part-2/mcp-through-the-broker/). The `ANTHROPIC_API_KEY=sk-ant-preflight-invalid-key` in front replaces the key for this one command, so Claude Code connects its MCP server and stops at its first model call; nothing is billed.

The run's own policy file, `$HOME/box-ws/r/<box ID>/policy.dw` (the box ID is in the `box: running profile ws with box ID ...` line), holds your rule at line 4, before the generated rules.

<Expect>

```text
"name":"cloudflare","status":"connected"
```

</Expect>

<Why title="Why a forbid on the tool's own action">
The rule names the tool in its head (`cloudflare::Action::"execute"`). That is the shortest rule that says "never this tool", and it is the form Box's MCP policy guide uses for refusing one tool. If it ever failed to load, Box would refuse every call to `execute` (a rule that names the tool in its head fails closed).

<Fragment slot="alternative">
The same constraint can be written on `mcp:call`: `forbid (principal, action == Box::Action::"mcp:call", resource) when { context.input.server == "cloudflare" && context.input has tool && context.input.tool == "execute" };`. It does not wait for the server's tool list. Not checked for this tool in this workshop; the same form is used in the tool-allowlist act.
</Fragment>
</Why>

</Iteration>

<Aside type="caution" title="A typo fails open">
Change `"execute"` to `"excute"` and run the free check. `box profile show ws` still passes, and the terminal prints one warning:

```text
strands-box: warning: a per-tool rule never loaded for ["cloudflare"]; the calls it decides are refused — check its tool and argument names against what the server declares, permit the server's tools/list, or remove the rule
```

A rule that names a tool the server does not have pins nothing, so the real `execute` would run. Read the terminal after the first run of every per-tool rule. Then put `"execute"` back.
</Aside>

### What the agent received

The refusal reaches Claude Code as an MCP error (JSON-RPC code `-32001`) whose text ends with your description:

```text title="The refusal, as the model saw it"
per-tool gate (cloudflare::Action::"execute"): policy denied this operation on 'cloudflare/execute' [policy: no_hidden_api_calls]: Cloudflare's execute tool runs its script on Cloudflare's side, where Box cannot see which API calls it makes. Use a tool whose calls Box can decide.
```

### The answers, in outline

In both measured runs the agent said it could not do the task, named the rule, and said it did not try to get around it. For the logs task it then wrote out a `curl` command for the developer to run outside the box. For the allowed task it suggested `npx wrangler deployments list`.

## Why search and docs cannot do the allowed task

The code-mode server offers five tools: `docs`, `execute`, `search`, `submit_feedback` and `whoami`. In Cloudflare's code-mode design, `search` finds operations in the description of Cloudflare's API and `docs` searches Cloudflare's documentation. They tell the agent which request would list the Workers. Only `execute` runs code that sends that request ([MCP servers and code mode](/part-1/mcp-and-code-mode/)). So the logs task searched three times, read the docs once, wrote its script, and was refused at the last step; the allowed task went straight to `execute` and was refused at once. With `execute` gone, the server can describe the API but cannot use it.

## The two seats

<Seat who="security">
The constraint holds: no script runs on Cloudflare's side, so neither the logs nor the attendee data can come back through this server. The records name the rule for each refusal. But the rule is all or nothing. The policy still cannot tell a request for the Worker list from a request for the logs, because both would arrive as `execute`. And the agent handed the developer a `curl` command that does outside the box what the box refused.
</Seat>
<Seat who="developer">
Both tasks fail, including the one the team agreed is fine. The logs task cost more than the allowed one because the agent searched and read the docs before it tried `execute`. The agent was honest about the refusal, and its suggestions move the work out of the box, where nothing is recorded.
</Seat>

**The takeaway:** refusing a tool by name is easy to write and hard to get around, but in code mode it refuses everything, so control costs usefulness.

## What to remember

- A policy file sits next to `profile.toml` and is named in `policies`; `box profile show ws` finds a missing file before any run.
- `forbid (principal, action == cloudflare::Action::"execute", resource);` refuses one tool of one server by name. The agent still sees the tool; the call is refused.
- A misspelled tool name loads with a warning and refuses nothing. Read the terminal after the first run.
- In code mode one tool does all the work, so a rule on tool names can only allow everything or nothing.
