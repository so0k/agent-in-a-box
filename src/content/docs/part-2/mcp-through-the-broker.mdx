Three pieces are new in the picture: the **MCP broker**, the **policy engine** with its policy files, and the **records**. The policy engine has been deciding since the first run on the previous page (the refused Datadog host was its answer); it gets its own piece now because, from here on, its rules are what the story is about.

## Two ways an MCP server reaches a boxed agent

An MCP server is a program that offers an agent tools over the Model Context Protocol (Part 1). In a box there are two kinds, and Box treats them differently:

- **A remote server**, reached over HTTP. Cloudflare's server at `mcp.cloudflare.com` is one. Its requests leave the box like any other request, through the egress gateway. When the host is one the profile declares as an MCP server, the gateway reads each request as MCP and asks the policy engine to decide an `mcp:call`. The four boxed acts before request-rules use this kind.
- **A local server**, a program on your machine that talks over its standard input and output (stdio). Here the **MCP broker** comes in. The agent runs a small alias named after the program; the alias talks to the broker; the broker starts the declared server in a sandbox of its own, after a `shell:spawn` decision, and asks the policy engine to decide each `mcp:call`. Part 5's local exec proxy is this kind.

This page is named after the broker, but a remote server such as Cloudflare's never passes through it: its requests go through the egress gateway. The decision is the same either way: one `mcp:call` per request, decided by the same policy engine, recorded in the same records. Only where it is made differs: at the gateway for a remote server, in the broker for a local one (Box docs, `docs/design/architecture.md`).

### Two declarations that must agree

Claude Code and Box each need to be told about the server, in their own file:

| | Claude Code's `--mcp-config` file | The profile's `[mcp.<name>]` table |
|---|---|---|
| Read by | Claude Code | Box |
| Says | what to connect to: the URL, or the command to start | which traffic is this server, so Box can recognise it, decide it and type its tools |
| For a remote server | the URL, here `https://mcp.cloudflare.com/mcp` | `destinations = ["mcp.cloudflare.com"]`: the host must match the URL's host |
| For a local server | `command` and `args` | `command`, with the same program and the same arguments in the same order |

If they do not agree, Box does not see MCP at all. For a remote server whose host is not declared, Box decides only `net:connect` and `http:request`; no `mcp:call` and no per-tool rule applies (`docs/user/mcp-policy.md`). That is why the profile, not Claude Code's file, is the security engineer's file.

Box never reads a project's `.mcp.json`: the agent could change it.

## What Box sees of an MCP request

An `mcp:call` decision gets these fields (`docs/user/policy/actions.md`):

- `server`: the name of the `[mcp.<name>]` table, here `cloudflare`.
- `method`: the MCP method, such as `tools/list` (what tools do you have?) or `tools/call` (run this tool).
- `tool`: for a `tools/call`, the tool's name, such as `execute`.

In the history, the RESOURCE column reads `server/method` for a listing (`cloudflare/tools/list`) and `server/tool` for a call (`cloudflare/execute`).

Box also reads the server's own `tools/list` reply and builds one typed action per tool, so a rule can look at a tool's arguments (Part 4). What Box does **not** see is what a tool does once the server runs it. And by default the records do not hold a tool call's arguments or its output.

## The check for this page

Every iteration below uses one free check, now with the MCP server. It writes Claude Code's output to a file, because the first line of that output tells you whether the server connected.

<Command what="Starts Claude Code in the box for one headless turn, with Cloudflare's MCP server and nothing else, and an invalid model key so nothing is billed.">

```sh
ANTHROPIC_API_KEY=sk-ant-preflight-invalid-key box run ws --no-banner -- --bare --strict-mcp-config \
  --mcp-config cloudflare-code-mode.json --tools "" --allowedTools mcp__cloudflare \
```

**The run.** The same check. **What we see.** The init line still says `"status":"failed"`, but the history has changed:

<Expect>


Box let the request through, and read it as MCP: `cloudflare/initialize` is the first MCP message, the handshake. This time Cloudflare refused it. The agent has no `CLOUDFLARE_MCP_TOKEN` (Box passes no token from your shell to the agent), so Claude Code filled in an empty value and sent `Bearer ` and nothing.

<Why title="Why an [mcp] table, not a route">
A route, `[egress.cloudflare-mcp]`, would open the host and nothing more: Box would decide connections and HTTP requests, and never see a tool call. The `[mcp.cloudflare]` table makes Box **identify** the server. Every MCP request becomes an `mcp:call` with the server, the method and the tool, and Box reads the server's `tools/list` to type each tool for later rules.

```text title="Part of box profile show ws --full"

@id("route_anthropic_request") permit (principal, action == Box::Action::"http:request", resource) when { context.input.host == "api.anthropic.com" };
@id("mcp_cloudflare_call") permit (principal, action == Box::Action::"mcp:call", resource) when { context.input.server == "cloudflare" };
@id("mcp_cloudflare_connect") permit (principal, action == Box::Action::"net:connect", resource) when { (context.input.host == "mcp.cloudflare.com" && context.input.port == 443) };
```

## Where a run's records are

Each run has a folder, `$BOX_HOME/r/<box ID>/`. After the checks above it holds:

```text title="$HOME/box-ws/r/b-<16 hex>/"
box.toml        the configuration Box Core ran with
policy.dw       the rules it ran with (your files first, starting with the starter policy.dw, then the generated ones)
profile-name    the profile's name, the only place a run records it
records.jsonl   the run's records
box/            Box Core's state: the aliases, the socket, the certificate authority, and the decision history
```

There are two stores of what happened, and the box CLI reads one of them:

- **The decision history** is the policy engine's own store, inside `box/private/`. `box runs history` reads it. The engine also uses it for rules that count (Part 3).
- **`records.jsonl`** holds the records in OpenTelemetry's JSON format (OTLP): every permit and every deny, Box's own control records, and logs Claude Code sends through the box. It is written where the agent cannot reach it. The Box docs call it diagnostic, and it is not tamper-evident.

Neither holds an MCP tool call's arguments or its output by default. A profile can add a telemetry target that does (`mcp_tool_calls` in `docs/user/telemetry.md`); not tried in this workshop. In this story such a target would store whatever the agent read, including attendee data.

`records.jsonl` can be followed while it grows:

<Command what="Prints new lines of the records file as Box writes them.">


<Flag name="-f">Keep the file open and print lines as they are added. Stop with Ctrl+C.</Flag>

<Seat who="security">

## What to remember

- A remote MCP server's requests go through the egress gateway; a local one is started by the **MCP broker**. Either way, each request is one `mcp:call` decision with `server`, `method` and `tool`.
- Claude Code's `--mcp-config` says what to connect to; the profile's `[mcp.<name>]` makes Box **recognise** the server. Without the table, Box sees only network requests.
- Declaring `[mcp.<name>]` generates `mcp_<name>_call`, which permits every tool of the server.
- `box runs history <BOX ID>` reads a run's decisions, also while it runs; `records.jsonl` in the run folder holds the raw records.
