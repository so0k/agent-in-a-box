In this act you point the agent at Cloudflare's per-endpoint server and write the security engineer's constraint as an allow-list: six tool names that read the Workers and their deployments, and every other tool of 3,053 refused. You will see the logs tool refused by name, and you will see why the plain "allowed" task is only half done.

## Where we are in the story

The deny-execute act kept the logs and the attendee data of the workshop progress tracker safe by refusing `execute`, and in doing so refused the work the team wanted done too. The developer still wants the agent to list the Workers and check the deployment of `box-poc-workshop`. The security engineer agrees, as long as the agent cannot read the logs or the attendee registry, and cannot deploy or delete. With one tool per operation ([The per-endpoint catalog](/part-4/per-endpoint-catalog/)), those are separate names.

## Write the allow-list

<Iteration n={5} title="Six tools may run, the rest are refused">

**What we add.** A new policy file in place of `no-remote-execute.dw`, which this catalog makes pointless (there is no `execute` here). Change line 5 of `profile.toml`; the starter file `policy.dw` stays first:

```toml title="$HOME/box-ws/profiles/ws/profile.toml (lines 4 and 5)" ins={2}
packs = ["@box/claude", "@box/anthropic"]
policies = ["policy.dw", "operate-tools.dw"]
```

The new policy file goes next to `profile.toml`, and the workspace now holds both MCP config files:

<FileTree>

- box-ws/
  - profiles/
    - ws/
      - profile.toml you edit this
      - policy.dw the starter, still first
      - no-remote-execute.dw no longer listed
      - **operate-tools.dw** the allow-list
  - storage/ kept between runs
  - r/ one folder per run
- leaderboard-ops/ the workspace
  - cloudflare-code-mode.json
  - **cloudflare-per-endpoint.json** the per-endpoint server, from iteration 2

</FileTree>

The old file can stay on disk; it is no longer listed. Then create `$HOME/box-ws/profiles/ws/operate-tools.dw`. Build it in this order:

1. **The comment** states the constraint in the story's words and names the tools it keeps out: `o11y_telemetry_query` (the Worker's logs), `d1_query` (the attendee registry), and every deploy or delete tool.
2. **The id and the description**: `operate_tools_only`, and a reason the agent can act on.
3. **The effect and scope**: `forbid` on `Box::Action::"mcp:call"`, the decision every MCP request gets. Not a per-tool action: a rule on `mcp:call` can be checked before the catalog is staged, so it loads when the box starts.
4. **`when`**: the rule is about the cloudflare server, and only about tool calls (`method == "tools/call"`). Listing the tools (`tools/list`) must stay permitted, or the agent gets no tools at all.
5. **`unless`**: the exception, "a tool call whose tool is one of these six". `context.input has tool` comes first because `tool` is optional in an `mcp:call`, and Box refuses to load a rule that reads an optional field without testing it. `.contains` tests whether the list holds the tool name. This page uses `has` and `unless` only as far as this rule needs them; [Rules on a tool's arguments](/part-4/policy-on-arguments/), two pages on, introduces them in full.

```text title="$HOME/box-ws/profiles/ws/operate-tools.dw"
// The security engineer's constraint, written for the one-tool-per-operation server: the agent
// may run only the tools that read the Workers and their deployments. Every other tool of the
// 3,053 is refused, among them o11y_telemetry_query (the Worker's logs, which hold attendee
// names and emails), d1_query (the attendee registry) and every deploy or delete tool.
@id("operate_tools_only")
@description("Only the tools that read the Workers and their deployments may run. The Worker's logs and the attendee data hold names and emails, and the agent may not deploy or delete.")
forbid (principal, action == Box::Action::"mcp:call", resource)
when { context.input.server == "cloudflare" && context.input.method == "tools/call" }
unless {
  context.input has tool && [
    "workers_legacy_scripts_list",
    "workers_legacy_scripts_get",
    "workers_legacy_scripts_scriptAndVersionSettings_get",
    "workers_legacy_scripts_content_get",
    "workers_legacy_scripts_versions_list",
    "workers_deployments_list"
  ].contains(context.input.tool)
};
```

The six tools read the Worker list, one Worker, its settings, its code, its versions and its deployments. All six names are in the catalog Claude Code received (checked against the tool list in the free check's first line), as are `workers_list`, `workers_get`, `o11y_telemetry_query` and `d1_query`.

**The run.** `box profile show ws` passes. Then the same free check as in iteration 3.

**What we see.** The server connects with 3,053 Cloudflare tools (3,054 in all, with `ToolSearch`), and no warning is printed. In the measured check on 2026-11-24, with the fork build, the hand-over took 65 seconds and the run 67.5 seconds.

<Expect variant="permit">

```text
"name":"cloudflare","status":"connected"
```

</Expect>

<Why title="Why forbid ... unless, on mcp:call">
`forbid ... unless` refuses every tool call except the listed ones, and is the only way to narrow the generated `mcp_cloudflare_call` permit ([Policy basics](/part-3/policy-basics/#a-permit-only-widens)). Writing it on `mcp:call` means it is checked and loaded when the box starts, and `box profile show` can catch a mistake in it. A misspelled name in the list does not fail open: that tool is simply refused too (reasoned from the rule's shape, not run).

<Fragment slot="alternative">
Box's MCP policy guide writes an allow-list as a `permit` that names the tools. With the box CLI the server's permit is generated from `[mcp.cloudflare]` and admits every tool, so that form would add nothing. Another alternative is one `forbid` per dangerous tool, but with 3,053 tools a list of what is allowed is much shorter than a list of what is not, and a new tool in the catalog stays refused.
</Fragment>
</Why>

</Iteration>

## What you see

The decisions below were measured on 2026-11-24 with the fork build, as `box runs history <box ID>` printed them. Every history starts with `installed policy policy.dw`; the time column, `net:connect` rows and the gateway's `http:request` rows are left out.

### The logs task: refused by name

<Expect variant="refuse">

```text
installed  policy    policy.dw                        -
permit     mcp:call  cloudflare/resources/list        mcp_cloudflare_call
permit     mcp:call  cloudflare/tools/list            mcp_cloudflare_call
deny       mcp:call  cloudflare/o11y_telemetry_query  operate_tools_only  a forbid rule matched
```

</Expect>

The model loaded `o11y_telemetry_query` with `ToolSearch`, called it, and got the refusal:

```text title="The refusal, as the model saw it"
mcp:call gate (server "cloudflare" method "tools/call"): policy denied this operation on 'cloudflare/o11y_telemetry_query' [policy: operate_tools_only]: Only the tools that read the Workers and their deployments may run. The Worker's logs and the attendee data hold names and emails, and the agent may not deploy or delete.
```

Before that call, the model tried Claude Code's `Bash` tool once, with `date +%s`, to read the time. Claude Code refused it (`Error: No such tool available: Bash. Bash is disabled for this session, in subagents as well as here.`), because `--tools ToolSearch` leaves no shell, and Box saw nothing of it. Whether the pack's system prompt led to that call is not known. The model then queried a whole day it chose itself.

The answer said the box's policy `operate_tools_only` denied the call, and that it had not tried another route, "since that would work around the policy". It offered two ways on: add a permit to a policy file in the profile "then press Ctrl+Alt+R", or run `npx wrangler tail box-poc-workshop` or open the Cloudflare dashboard yourself. (The pack's system prompt tells the agent about the banner and Ctrl+Alt+R, even in a run with `--no-banner`: [Inside the pack](/part-2/inside-the-pack/).) The extra turn took the run to USD 0.2537, over its cap of 0.25. Claude Code ended it with `error_max_budget_usd`, so the answer is in the stream but there is no result event.

### The allowed task: half done

<Expect variant="refuse" title="What you should see: one refused, one permitted">

```text
deny    mcp:call  cloudflare/workers_list              operate_tools_only  a forbid rule matched
permit  mcp:call  cloudflare/workers_deployments_list  mcp_cloudflare_call
```

</Expect>

The model loaded three tools with `ToolSearch`: `workers_list`, `workers_deployments_list` and `workers_legacy_scripts_list`. It called `workers_list` for the Worker list, which is refused, and `workers_deployments_list`, which runs. The answer: the Worker list was blocked, and here is the current deployment of `box-poc-workshop` (one version at 100 percent, created 2026-11-24 05:09 UTC, 5 deployments in all). It put the block down to "the Cloudflare MCP server's `operate_tools_only` policy", although the rule is the box's. It said it had not tried other tools to get the list another way, and offered to try `workers_legacy_scripts_list` if told to.

This is the honest result of a tool-name allow-list. Cloudflare's API has two operations that list Workers: the older one, behind `workers_legacy_scripts_list`, which is on the list, and a newer one, behind `workers_list`, which is not. The model picked the newer one. An allow-list of names must name every tool a model might pick for the same job. The security engineer chose six tools from the operations the team agreed on; the model chose a seventh.

## The two seats

<Seat who="security">
The policy now sees which operation the agent asks for, and refuses the logs by name before the request reaches Cloudflare. A new tool in the catalog is refused until someone lists it. But the allow-list is only as good as its names: the model reached for `workers_list`, which the security engineer did not think of. And an allowed tool's answer is not checked: the deployments list returned the deployer's email address in its metadata.
</Seat>
<Seat who="developer">
The deployment question is answered and the logs are refused, but the Worker list is not, unless the developer steers the model to a listed tool or asks the security engineer to widen the list. Every run waits about a minute for the catalog and costs about $0.22 to $0.25, against $0.0098 and $0.0185 for the deny-execute act's runs in code mode.
</Seat>

**The takeaway:** with one tool per operation the policy can allow reads and refuse the logs by name, but a list of names refuses whatever tool the model picks that nobody listed.

## What to remember

- Part 4 runs on the fork build: put `$HOME/box-build` first on the `PATH`, and `box --version` prints `box 0.1.0`.
- `?codemode=false` in the MCP config file switches the server; the profile does not change.
- Raise `MCP_TIMEOUT` in `[agent.env]`, or Claude Code starts before Box has staged the catalog and has no tools.
- An allow-list is `forbid` on `mcp:call` with `when` (this server, tool calls) and `unless` (`has tool` and the list `.contains` it). It loads at start.
- A list of tool names must hold every tool a model may pick for the job. Read the refusals: they tell you which names are missing.

The security engineer also wants to say which account a listed tool may be used on. [Rules on a tool's arguments](/part-4/policy-on-arguments/) shows how.
